# Media and image cache

- **`Media.alt` has two values during a request.** `MediaExtension::media_from_string()`
  calls `setAlt($caption, true)` whenever content containing `![caption](src)` renders,
  mutating alt **in memory only** — the DB still holds the previous value, and the render
  runs before `AfterEntityUpdatedEvent`. Any rename or diff heuristic must read the
  *persisted* alt via `getUnitOfWork()->getOriginalEntityData($media)['alt']`, not the
  live one. `Media::isFileNameAutoGenerated(?string $referenceAlt)` takes the reference
  alt for exactly this reason.
- **A 0-byte derivative means an in-place optimizer truncated it, not an encode failure.**
  `ImageEncoder` (vips) is atomic and rejects empty payloads — a real encode failure
  throws and leaves the file *missing*. A genuinely 0-byte file is the fingerprint of an
  external binary writing its own target (`cwebp … 'x.webp' -o 'x.webp'`) and being killed
  mid-write. Optimize into a temp copy, validate (non-empty + `getimagesize`), then
  atomically rename. Treat 0-byte cache files as missing everywhere they are read.
- Generalize that shape: any "truncated cache file, non-deterministic, size-correlated,
  silent RC=0" symptom points at an external binary writing in place, not at the primary
  encoder.
- **Derivatives are written to `pw.media_cache_dir`, never to `public_dir`/`public_media_dir`.**
  The default is `public/{public_media_dir}/`, so nothing moves for a site; `public_media_dir`
  alone stays what the *browser* path is built from. Compute a derivative path from anything
  else and you reintroduce the leak that made a `pw:static` build ship 17k OG images of pages
  that only ever existed inside a test.
